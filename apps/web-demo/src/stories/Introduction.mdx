# Design system

Components live in `packages/` and are consumed by the demo apps in `apps/`.

- **`@dsm/shared`** — the platform-agnostic contract: base types and design tokens.
- **`@dsm/web`** — the React implementation, styled with plain CSS.
- **`@dsm/mobile`** — the React Native implementation, styled with `StyleSheet`.

## Same contract, same tokens

The two implementations share the props contract (`IButtonBaseProps` from
`@dsm/shared`) **and the resolved token values**, so today they look the same.
Divergence is allowed where a platform genuinely calls for it, but neither
implementation invents a value: both read the same bDS tokens for the active
theme and apply them inline.

That is why the **Theme** dropdown works on both at once — there is no
stylesheet or CSS cascade involved on either side. It also means the differences
that remain are behavioural rather than visual: web tracks `hover` (a touch
screen has none) and mobile adds `hitSlop` for the sizes that fall below the
minimum touch target.

## Adding a component

Each component is a folder of four files — see `Button`, `TextField` or
`TextArea`:

```
Button/
├── index.ts           # public barrel
├── Button.tsx         # presentation; owns the interaction state
├── Button.types.ts    # props, extending the shared base contract
└── useButton.ts       # resolves tokens for the active theme + that state
```

Mobile adds a `Button.styles.ts` for the layout that never changes with theme or
state. Neither platform ships a stylesheet for the component itself.

The shared contract goes in `@dsm/shared` first, without event handlers — each
platform adds its own (`onClick` vs `onPress`).
